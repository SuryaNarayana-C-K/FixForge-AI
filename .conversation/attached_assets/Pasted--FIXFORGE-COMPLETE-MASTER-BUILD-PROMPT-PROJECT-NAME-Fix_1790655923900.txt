# 7. CORE PROBLEM

Developers spend significant time debugging:

* syntax errors
* runtime errors
* failed tests
* incorrect logic
* dependency issues
* regression failures
* CI failures

Existing coding assistants can suggest or generate fixes.

However, FixForge focuses on the complete autonomous loop:

```text
Generate Fix
      ↓
Actually Execute It
      ↓
Actually Test It
      ↓
Observe Failure
      ↓
Understand Failure
      ↓

      ↓

      ↓
Verify
```

Never declare a repair successful simply because an LLM generated code.

# 12. TOOL SECURITY

Never allow the AI agent to execute arbitrary commands directly on the host machine.

All repository code execution must happen inside Docker.

Validate:

* file paths
* commands
* working directory
* repository boundaries

Prevent:

```text
../../
```

path traversal.

Prevent:

* absolute host paths
* symlink escapes
* host filesystem access
* Docker socket access
* environment secret access

---

# 13. DOCKER SANDBOX

The sandbox is one of the most important components.

Every repair job gets an isolated environment.

Example:

```text
Repair Job
    ↓
Create temporary workspace
    ↓
Create Docker container
    ↓
Copy repository
    ↓
Install dependencies
    ↓
Run tests
    ↓
Capture output
    ↓
Destroy container
```

Container requirements:

* non-root user
* CPU limit
* memory limit
* process limit
* execution timeout
* filesystem isolation
* configurable network restriction
* no Docker socket
* no host secrets

Never mount:

```text
/var/run/docker.sock
```

into the sandbox.

# 20. PATCH GENERATION

Prefer structured patches/diffs.

Do not blindly regenerate entire files.

Patch should contain:

* old content
* new content

Return patch conflict to the agent.

# 21. SELF-CORRECTION

This is the primary feature of FixForge.

Example:

```text
Attempt 1
─────────
Patch generated
Tests: FAILED

        ↓

Analyze new failure

        ↓

Attempt 2
─────────
New patch generated
Tests: FAILED

        ↓

Analyze again

        ↓

Attempt 3
─────────
New patch
Tests: PASSED
```

The agent must remember previous attempts.

Do not repeatedly apply the same failed patch.

Store:

* hypothesis
* patch
* changed files
* test result
* error
* reason for failure

# 22. PREVENT REPEATED FAILURES

Before generating a new patch:

Give the agent previous attempts.

```text

Reason:
Expected fallback value was still incorrect.
```

The next agent iteration must explicitly consider previous failures.

# 49. AGENT SYSTEM PROMPT

The AI repair agent should follow these rules:

```text
You are FixForge, an autonomous software repair agent.

Your goal is to repair software failures and provide execution evidence that the repair works.

Rules:

1. Inspect before editing.
2. Reproduce the failure whenever possible.
3. Identify evidence for the root cause.
4. Make the smallest safe change.
5. Never claim success without test evidence.
6. Run tests after modifications.
7. If tests fail, analyze the new failure.
8. Do not repeat a failed patch without a new hypothesis.
9. Remember previous attempts.
10. Do not modify unrelated code.
11. Stay inside the assigned repository.
12. Never access host secrets.
13. Never execute code outside the sandbox.
14. Stop after the maximum number of iterations.
15. Produce a final structured report.
```
